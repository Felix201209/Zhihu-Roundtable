# 黑客松来源记录

本文件用于说明仓库内 plan、readiness、API contract 的信息来源，避免路演时把内部整理误说成官方承诺。

## 1. 赛事手册截图

来源：Felix 在 2026-05-09 提供的《知乎 Hackathon 2026 | AI 脑洞实验室 开发者手册》截图。

仓库没有提交原始截图文件，原因是：

- 提交包要保持轻量，避免把本地截图、水印和临时图片塞进代码仓库。
- 评委真正需要的是可验证实现、运行命令和接口映射，不是截图备份。
- 如果现场需要展示原始资料，直接使用本机截图或官方页面。

当前实现引用的手册信息包括：

- 赛事方向：灵感引擎、引力场、刘看山。
- 交付材料：可运行体验链接、产品说明、代码仓库链接。
- 评审维度：AI 场景价值、创新度、完成度、产品体验与设计感、计划书和演示环节。
- 接入能力：圈子、热榜、知乎搜索、全网搜索、评论、reaction、发布。
- 路演要求：Demo 实操为主，可配合 PPT 讲解，Q&A 简短回答。

## 2. 原始 30 节产品方案

来源：Felix 在本项目早期确定的《知辩圆桌｜刘看山主持的知乎 AI 观点实验室》30 节方案。

仓库中的 `plan.md` 是后续冲刺执行计划，不是原始 30 节正文。当前保留两类证据：

- `docs/original-plan-coverage.md`：把原始 30 节逐项映射到当前实现。
- `docs/hackathon-demo-plan.md`：把产品逻辑压缩成路演脚本和评委问答。

原始方案的核心判断是：

- 不是做 AI 写知乎回答，而是做 AI 组织知乎讨论。
- 必须从知乎热榜开始，并回到圈子/评论。
- 刘看山是主持人，不是陪聊 bot。
- 后端用固定状态机组织多 Agent，不做不可控自由群聊。
- 黑客松版砍掉多人在线、复杂 3D、积分系统和自动无限辩论。

## 3. Readiness 自检的边界

`POST /api/readiness` 和前端“夺奖自检”不是替评委打分，也不承诺比赛结果。

它的用途是把赛事手册里的评分维度变成工程检查表：

- 哪些能力已经有代码和测试证据。
- 哪些能力只在 mock-safe 演示里完成。
- 哪些能力依赖官方素材、token 或线下权限。
- 路演时应该优先展示哪些证据。

因此 UI 只显示“就绪 / 评分维度就绪”，不再显示“100 分”式自评分。

## 4. API 接入边界

当前 provider 已按手册截图里的能力设计 live-ready wrapper，但真实发布、评论和 reaction 仍依赖正式 token、权限和官方开放窗口。

实现原则：

- 读接口可以 fallback 到缓存/Mock，保障路演不被外部网络卡死。
- 写接口在 live 模式下必须用户确认，且失败不能伪装成 mock 成功。
- `ZHIHU_API_BASE_URL` 只允许 `https://*.zhihu.com`，防止 token 打到错误域名。
- Demo 默认 mock-safe，现场切 live 前必须先确认 token 和权限。
